# 재검토 결과

Fields.kt 전체, PleosLibraryUiTest.kt의 마지막 테스트 3개(`:583-662`), Navigation.kt의 Tabs 검증 부분(`:97-117`)을 읽었습니다. 빌드와 테스트는 실행하지 않았습니다. 아래 내용은 모두 코드를 읽고 내린 판단입니다.

결론부터 말씀드리면, 기존 지적 2건 중 NumberField는 해결되었습니다. TextField 커서 클리핑은 일부만 해결되어 P2 1건이 남아 있습니다.

## 남은 결함

**1. TextField: 끝 커서가 여전히 고밀도 화면에서 일부 잘림 (P2)** (`Fields.kt:112`, 관련 `:214-231`)

- 콘텐츠 폭에 커서 폭만큼 오른쪽 패딩을 넣은 부분(`:229-231`)은 올바릅니다. 이 덕분에 `maxValue`가 `텍스트 폭 + cursorWidth(px) - viewport`가 되었습니다.
- 문제는 스크롤 목표를 정하는 `:112`가 여전히 `cursor.right + innerOffset.x + 4`라는 점입니다.
  - 여기서 `4`는 dp가 아니라 px로 고정된 값입니다.
  - `getCursorRect`는 폭이 0인 rect를 돌려주므로 `cursor.right`와 `cursor.left`가 같습니다.
- 그 결과 실제 동작은 이렇습니다.
  - 커서를 그리는 폭(3dp)이 4px보다 크면, 즉 density가 약 1.34보다 크면 스크롤은 `maxValue`까지 가지 않고 `텍스트 폭 + 4px`에서 멈춥니다.
  - 커서는 `[텍스트 폭, 텍스트 폭 + 3dp]`에 그려지므로, 오른쪽 `3dp - 4px`는 clip에 잘립니다.
  - 예를 들어 density 3에서는 9px 중 4px만 보입니다.
- 지난번처럼 커서가 완전히 사라지지는 않으므로 결함 수준은 줄었습니다. 그래도 끝 입력이라는 가장 흔한 경로에서 커서가 토큰 폭보다 좁게 보입니다.
- 테스트 영향: `longEditorKeepsTrailingCursorInsideViewport`(`PleosLibraryUiTest.kt:628`)는 오른쪽 끝에서 33.5dp 지점, 즉 viewport 끝에서 1.5dp 안쪽을 샘플링합니다. 보이는 커서 폭이 4px이므로 이 테스트는 density가 약 2.67 이하일 때만 통과하고, xxhdpi(3.0) 기기에서는 실패할 것으로 예상합니다. 실행하지 않았으므로 실제 결과는 확인하지 못했습니다. 이 실패는 테스트가 틀린 것이 아니라 위 결함을 정확히 드러내는 것입니다.
- 수정안: `:112`를 `(cursor.right + innerOffset.x).toInt() + with(density) { m.dp("fields/text/cursor_width", 3f).roundToPx() }`처럼 커서 폭의 px 값으로 바꾸십시오.
  - LaunchedEffect 안에서 쓸 수 있도록 `LocalDensity.current`를 composable 범위에서 받아 두어야 합니다.
  - 이렇게 하면 `maxValue`와 같은 기준이 되어 커서 전체가 보입니다.
- 부수 사항: 같은 테스트의 `33.5f`는 `fields/text/medium/padding_horizontal`이 32라는 가정, 즉 connect-s 모드를 전제로 합니다. 토큰 표상 이 값은 connect-l/w에서 28, waterfall에서 35이므로, 테스트 기본 모드가 바뀌면 깨질 수 있습니다. 결함이라기보다는 테스트가 깨지기 쉬운 부분입니다.

## 해결 확인

**NumberField 재탭 시 IME 재요청** (`Fields.kt:400`, `:462-473`)
- 클릭 블록에서 `requestFocus()` 다음에 `keyboard?.show()`를 호출합니다. 이미 포커스가 있는 상태에서 Back으로 IME를 닫은 뒤 다시 탭하는 경로가 이제 처리됩니다.
- 처음 탭할 때는 포커스 전환과 함께 입력 세션이 시작된 뒤 `show()`가 호출되므로 문제가 없습니다.
- 지난번 참고 사항이던 덮어쓰기도 반영되었습니다.
  - 기존 칸을 탭하면 `TextRange(i, i + 1)`로 선택하고, 강조 기준도 `selection.start`로 맞췄습니다(`:460`, `:468`).
  - KDoc의 "기존 칸 탭은 해당 자리 덮어쓰기"(`:366`)와 구현이 일치합니다.
  - 입력값을 처리하는 `mapped()` 로직(`:413-422`)도 선택 영역을 덮어쓴 뒤 커서를 i+1에 둡니다.
- 테스트 `numberCellRequestsKeyboardAgainAndOverwritesSelectedDigit`(`:634-662`)의 좌표와 기대값도 맞습니다.
  - 클릭 좌표 `width/8`은 73dp로, 전체 폭 584dp 중 0번 칸 안입니다.
  - 기대값 `"0012"` → `"9012"`도 맞습니다.
  - 다만 fake controller의 `hide()`는 아무 동작도 하지 않습니다. 따라서 이 테스트는 실제 IME 표시 여부가 아니라 `show()` 호출 횟수만 검증합니다. 목적에는 충분합니다.

**`longEditorScrollAndNumberSelectionKeepCaret`** (`:583-605`): SetSelection(1,2) 후 "9"를 입력하면 `"0912"`가 됩니다. 구현과 일치합니다.

**Navigation.kt Box Tabs 개수 검증** (`:114-117`)
- Large는 6개 이하, Medium은 5개 이하로 검증하며, 최소 2개 조건도 함께 있습니다.
- `17_figma_tabs.md`의 solid variant 목록(Large Segments=2~6, Medium Segments=2~5)과 정확히 일치합니다.
- Line 스타일은 개수 제한에서 빠져 있는데, 이 역시 KDoc(`:98`)과 일치합니다. 문제 없습니다.

## 참고 (결함 아님, 의도 확인용)

NumberField에서 기존 칸을 덮어쓴 뒤 바로 다음 숫자를 입력하면, 커서가 i+1 위치에 선택 없이 놓여 있어 끼워 넣기로 동작합니다.
- 예: `"1234"`에서 0번 칸을 탭하고 9, 8을 입력하면 결과는 `"9823"`입니다.
- 이때 1번 칸이 강조되어 있으므로, 사용자는 연속 덮어쓰기 결과인 `"9834"`를 예상할 수 있습니다.
- KDoc은 탭한 자리의 덮어쓰기만 약속하므로 명세 위반은 아닙니다. 연속 덮어쓰기가 의도라면 onValueChange에서 선택 없는 커서가 `< accepted.length` 위치에 있을 때 `(sel, sel + 1)`로 선택을 넓히면 됩니다.

## 새 회귀

이번 변경 범위에서 P0/P1 회귀는 찾지 못했습니다.
- 오른쪽에만 준 패딩(`absolutePadding(right)`)은 왼쪽 원점을 바꾸지 않습니다. 그래서 `innerOffset.x`, 커서 그리기 좌표, LaunchedEffect의 스크롤 계산이 서로 같은 기준을 유지합니다.
- 짧은 텍스트에서는 `widthIn(min = viewport)` 때문에 스크롤이 생기지 않습니다.
